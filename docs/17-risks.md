| RISK-21 | GitHub's runner pool is heterogeneous, so a media fixture rebuilt on different hardware no longer matches the manifest | M | M | Discovered in M3.6: `libx264`, `libvpx` and `libopus` dispatch on CPU features and no ffmpeg flag reaches that choice (`-cpuflags 0` is byte-identical), so **CI's hardware is part of the reproducibility contract** (`06` §4). **This is CPU-dependence on a heterogeneous pool, not nondeterminism** — the reading matters: homogeneous hardware (a larger-runner label, or self-hosted) would recover reproducibility if it ever became worth paying for, whereas nothing recovers it if the encoders are genuinely nondeterministic. `ci.yml` logs each runner's CPU model and SIMD flags, and the `carry-forward-fixtures` artifact holds the only copy of those bytes until the deploy publishes them. **Retention measured 2026-09-10: 90 days**, read off the artifacts rather than off `retention-days:`, which a repository maximum can clamp silently. The window is not as tight as it sounds — every CI run re-uploads the artifact — but it is also narrower than it sounds, because only the run that produced a given set of bytes can fulfil the manifest entries adopted from it (three artifact sizes observed across runs: 68,840,997, 68,841,346 and 68,843,383 bytes, which is this risk visible in a listing). `09` §3.1 works it through. Published bytes stay frozen regardless — the deploy compares against the manifest and refuses to overwrite, so the failure mode is a red deploy, never a silently changed file. **Recovery, in order: red deploy -> supersede at a new path. Never regenerate and overwrite** — the published bytes are the product and stay as they are; the temptation under pressure is to 'fix' the manifest to match the new build, which is exactly what REQ-2 forbids. Mark the path `expected_drift` so `build --audit` stops reporting it as real drift (`06` §8). Immutability does not depend on reproducibility: it is held by the manifest lock and the R2 bucket locks, neither of which regenerates anything. Reproducibility is a convenience for audits and the *fallback* restore path — `11` §7.6 makes release archives primary — so the exposure is a compound failure of fleet drift **and** lost archives, for media only. Workflows pin `runs-on: ubuntu-24.04` to remove one axis of drift. Only 4 of 36 media fixtures are this sensitive; images, documents and data are not | `manifest check` reports differing bytes on `main` for a fixture nobody touched | A |
| RISK-22 | The cost model's two controls, and how far each actually reaches | L | M | **Both exist, verified M2.4 runs 7-9.** *404 caching*: 404s **are** cached (non-zero `Age` on the first sample of all three runs), so a repeated missing path is bounded; the duration is Cloudflare's documented 3-minute default and is unmeasured. *Rate limit*: enforces consistently **when the load reaches one counter** — runs 6 and 9 both fired at request 294, at 262 and 252 req/s from a single colo. **The limit that matters is the counting key**: the rule counts per `(ip.src, cf.colo.id)`, and one GitHub runner's traffic was spread across 3 and then 6 data centres, so a distributed client gets roughly N times the budget. Runs 4-5's apparent intermittency was this, not approximate counting. *The premise under both*: a missing-key GET **is** recorded as a Class B operation — 1,000 unique 404s produced exactly 1,000 `GetObject`/`userError` records on 2026-09-10, and the owner's free-tier consumption counter moved 1.89 k → 3.3 k across the same span (`19` §3.1). **Residual accepted-on-evidence**, where evidence means two agreeing consumption records and not an observed invoice. `19` §3's scenarios are unchanged; what changed is that both controls and their premise are now evidenced rather than assumed | `probe` reports `404-caching` or `rate-limit` failing from a **single** identity; `health.yml`'s `cost` issue on missing-key reads | A |
